## Staged repository improvement
`public/robots.txt` expresses `search=yes, ai-input=no, ai-train=no`, retains the sitemap and general search crawl permission, and asks known AI/training crawlers (including GPTBot, ClaudeBot, CCBot, Bytespider, Google-Extended, Applebot-Extended, meta-externalagent, and Amazonbot) to stay away. A source-level Vitest regression test checks the requested bot groups and that standard Googlebot/Bingbot are not directly banned. **Robots.txt is voluntary signaling and is not a security boundary; a crawler may ignore or spoof it.** Unpublished works must be protected by server authorization, not robots.txt. No public route, feature or art asset was removed.

## Supabase (read-only schema and advisor inspection)
Live security advisor reports 11 anonymous-callable and 147 authenticated-callable `public` SECURITY DEFINER functions; it also flags leaked-password protection as disabled and 69 RLS-enabled tables without direct policies. These flags are **review candidates**, not evidence of a breach. A table with RLS but no policies typically denies direct table access; an RPC may be deliberately used to expose constrained operations.

Storage buckets `comic-covers`, `comic-originals`, `comic-pages`, `duel-art` and `palace-chat-photos` are private. `profile-media` is public by design. Storage object policies include owner-based writes, restricted comic reader assets and conversation-member chat-photo reads, but no account-to-account adversarial tests were performed.

The current `public.works` RLS SELECT policy checks authorship/collaboration or publication+visibility+age. `public.chapters` uses `private.can_read_chapter`. `public.messages` SELECT checks conversation membership. `public.get_work_lore` presently includes signed-in gating for members-only material plus an age gate — the older reported guest-lore mismatch is no longer apparent from the live function definition.

**Specific review item:** `public.get_palace_praise_state(kind,id)` counts reactions without checking if the requesting identity may read the indicated work/chapter. When a private ID is known, aggregate reaction counts could be disclosed. A proposed, **unapplied** replacement is staged at `database/PROPOSED-restrict-praise-state-visibility-2026-10-31.sql`. It checks the same reader eligibility helpers as the work/chapter policies and returns neutral zero counts for inaccessible IDs. This SQL is not role-tested or applied; do not change the production function without controlled staging regression tests. An additional **unapplied** candidate, `database/PROPOSED-guard-bookmark-counts-by-reader-age-2026-10-31.sql`, adds reader-age eligibility to `get_reading_room_bookmark_counts`, while maintaining its 1–100 ID limit and published-only audience. The live function currently checks publication and public/members visibility but not the work's minimum reading age; this can reveal aggregate saves on age-restricted works to underage accounts or guests who know an ID. `tests/creator-privacy-sql-contract.test.js` provides structural checks for both SQL candidates **only**; it is not a database integration test. Further examine whether `get_work_lore` exposes an unpublished unlock-chapter title/identifier through its `unlock_chapter` field to non-owners. These are code-review concerns, not demonstrated access to manuscript text.

**Confirmed access-rule mismatch:** the public `get_grand_palace_identity(p_member)` RPC previously used only `p.visibility <> 'hidden'` (or caller is owner), while the ordinary profile SELECT policy uses `private.viewer_can_discover_profile(id)` for membership visibility, discovery preferences and user blocks. This can reveal limited Grand Palace membership/selected theme/honours information about a profile that should not be discoverable through the normal API if its UUID is known. The minimal **unapplied** proposal is `database/PROPOSED-guard-grand-palace-identity-discovery-2026-10-31.sql` and reuses the existing profile discovery function while preserving public identity, author access and the current JSON shape. No member profile was read or used to demonstrate a leak. Test owner, guests, members, blocked and discovery-private synthetic identities in staging before deploying.

Other schema-only review: enumerate each callable definer function, its parameters and output, its auth/visibility checks and its frontend callers before revoking grants. Verify `search_path` and function execution roles. Never blanket-revoke, add `USING(true)`, or disable RLS. Do not read private member records to test this.
